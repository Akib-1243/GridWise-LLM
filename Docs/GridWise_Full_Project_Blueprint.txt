GridWise — Full Project Blueprint
Below is the complete, spec-aligned plan: frontend (ReactJS), backend (PHP Laravel + Docker), ERD, and 3-member work division.

The backend is the judge-facing artifact (must expose GET /health and POST /optimize-energy). The frontend is a team-facing dashboard for testing, visualizing, and demoing — it is not what the judge calls, but it's needed for your video, local testing, and operator UX.

│                     │        │  POST /optimize-energy ──► LLM Service   │

│  - Case runner      │        │      Guardrail Validator                 │
│                     │        │            │                             │
└─────────────────────┘        │            ▼                             │
                               │      Optimization Engine (LP/MILP)       │
┌─────────────────────┐        │            │                             │
│  Judge Harness      │  HTTP  │            ▼                             │
│  (external)         │ ─────► │      Final Validator ──► JSON response   │
│  GET /health        │        │                                          │
│  POST /optimize-... │        │      MySQL: scenarios, runs, directives  │
└─────────────────────┘        └──────────────────────────────────────────┘
Critical rule: the judge only calls GET /health and POST /optimize-energy. Frontend must never be required for judging. All judge endpoints must be stateless, fast, and self-contained.

2.2 OptimizeEnergyController flow (exact)
text
1. Validate request (OptimizeEnergyRequest)
   → 400 malformed JSON, 422 semantic
2. Persist Scenario + Hours + Battery + Notes
3. LlmInterpreter::interpret(notes, scenarioContext)
   → structured directives (untrusted)
4. DirectiveGuardrail::validate(raw)
   → hours normalized, factors normalized, unknown → no_op
5. ConstraintBuilder::build(effectiveSolar, batteryRules, directives)
6. LpOptimizer::solve()  → hourly_plan
7. ScheduleValidator::replay(hourly_plan, directives, battery)
   → if invalid → repair or 500 controlled
8. Compute totals (total_grid_kwh, total_cost_bdt, peak_grid_kwh)
9. Return OptimizeEnergyResource  (exact schema)

4.1 Enum values
scenarios.source: manual, sample, judge

optimization_runs.status: success, failed, invalid

directive_interpretations.directive_type: solar_reduction, minimum_battery_reserve, no_charge_window, no_discharge_window, max_grid_window, no_op

hourly_plan_entries.battery_action: charge, discharge, idle

4.2 Notes on the ERD
structured_adjustment is JSON (MySQL JSON type) because shape varies by directive.

llm_call_logs stores no secrets — only metadata + sanitized response.

optimization_runs stores the computed totals for fast dashboard queries; the judge response is always recomputed from hourly_plan_entries to guarantee consistency.

UNIQUE(run_id, note_index) and UNIQUE(run_id, hour) enforce the exact one-per-note and 24-hour rules at DB level.

6. Work Division — 3 Members

Deliverables:

Prompt template that reliably extracts directive_type, hours, factor/minimum_energy_kwh/max_grid_kwh, and no_op.

Paraphrase robustness: "80% reduction" → factor 0.2; "1 PM to 3 PM" → [13,14]; "50% of capacity" → 100 kWh when capacity = 200.

Deterministic guardrail that never invents a directive — invalid LLM output → no_op.

GET /health returning {"status":"ok"} within 60s of boot.
